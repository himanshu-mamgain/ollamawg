# Configuration reference

`ollamawg` uses two YAML files:

- **`server.yaml`**, on the machine running Ollama. It holds the server's private key and the dashboard password.
- **`<device>.yaml`**, one per device. It holds that device's private key.

Both are written with mode 0600 and contain secrets. Never commit them; the repository's `.gitignore` excludes `*.yaml` at the root.

Unknown keys are rejected, so a typo like `listen_prot` fails loudly instead of being ignored.

## server.yaml

```yaml
server:
  private_key: kN0f...=              # base64, same format as `wg genkey`
  listen_port: 51820                 # UDP port for WireGuard
  address: 10.77.0.1/24              # server's tunnel IP + the pool devices get IPs from
  public_endpoint: vpn.example.com:51820   # written into new client configs
  upstream: http://127.0.0.1:11434   # where Ollama is
  proxy_port: 11434                  # TCP port of the proxy inside the tunnel
  mtu: 1420
  max_body_mb: 64                    # request body cap (images, long prompts)

admin:
  listen: 127.0.0.1:8088             # dashboard + admin API + /metrics
  password: 3vQ...                   # basic auth, user "admin"; empty disables the dashboard
  totp_secret: XIZL...               # optional: 2FA on (set by `ollamawg 2fa enable` or the dashboard)
  api_token: DXcK...                 # optional: bearer token for scripts and Prometheus
  access_log_file: /var/log/ollamawg/access.jsonl   # optional, one JSON object per request
  log_buffer: 2000                   # recent requests/events kept in memory

firewall:
  default: allow                     # allow | deny (deny = only "allow" rules get through)
  rules:
    - action: block
      cidr: 203.0.113.0/24
      note: scanner
      added: 2026-10-25T03:00:00Z
    - action: allow
      cidr: 198.51.100.7             # a single IP is fine; stored as-is

roles:                               # optional: override built-ins or add your own
  embedder:
    allow: ["/api/embed", "/api/embeddings", "/v1/embeddings", "/api/tags"]

peers:
  - name: laptop
    public_key: Hq3...=
    preshared_key: Z1x...=
    address: 10.77.0.2
    role: user
    models: [llama3.2, "qwen3:*"]    # optional allowlist; empty = all models
    rpm: 60                          # optional requests/minute; 0 = unlimited
    blocked: false
    created: 2026-10-25T03:00:00Z
```

### `server`

| Field | Default | Notes |
|---|---|---|
| `private_key` | generated | Rotating it means re-issuing every client config. |
| `listen_port` | `51820` | Changing it requires a restart. |
| `address` | `10.77.0.1/24` | Must be IPv4. Peers get unique IPs inside the prefix. |
| `public_endpoint` | from `init --endpoint` | Only used when generating client configs. |
| `upstream` | `http://127.0.0.1:11434` | Can point at another host on a private network. The exposure check is then skipped. |
| `proxy_port` | `11434` | The port clients dial inside the tunnel. |
| `mtu` | `1420` | Lower it, for example to 1280, on networks that drop large UDP packets (some mobile carriers, PPPoE). |
| `max_body_mb` | `64` | Larger bodies get `413`. |

### `admin`

| Field | Default | Notes |
|---|---|---|
| `listen` | `127.0.0.1:8088` | When bound to loopback, requests with any other `Host` header are refused, which prevents DNS rebinding. |
| `password` | generated | Set it to an empty string to turn the dashboard off. |
| `totp_secret` | none | Base32 TOTP secret. When set, the dashboard needs password + authenticator code and refuses basic auth. Remove it, or run `ollamawg 2fa disable`, to turn 2FA off. |
| `api_token` | none | Accepted as `Authorization: Bearer <token>` on every admin endpoint. Generated when 2FA is turned on. |
| `access_log_file` | none | Appended, never rotated by ollamawg. Use logrotate with `copytruncate`. |
| `log_buffer` | `2000` | Entries kept in memory for the dashboard. |

### `firewall`

Rules match the **source IP of UDP packets** arriving at the WireGuard port, which is the device's public IP and not its tunnel IP. The most specific prefix wins. On equal prefix length, `block` beats `allow`. When no rule matches, `default` decides.

Some example setups:

```yaml
# Block one abusive network, admit everyone else (keys still required)
firewall:
  default: allow
  rules:
    - {action: block, cidr: 203.0.113.0/24}

# Only your office and home connections may even attempt a handshake
firewall:
  default: deny
  rules:
    - {action: allow, cidr: 198.51.100.0/24, note: office}
    - {action: allow, cidr: 192.0.2.44, note: home}
```

### `peers`

| Field | Notes |
|---|---|
| `name` | Letters, digits, `-`, `_` and `.`. Must be unique. |
| `public_key` | The device's WireGuard public key. The device ID is the first 4 bytes of its SHA-256, shown in hex. |
| `preshared_key` | Optional extra symmetric key, which hardens the handshake against a future quantum adversary. Generated by `add-peer`. |
| `address` | One IPv4 address inside the server's prefix. |
| `role` | `user`, `readonly`, `admin`, or a name from `roles`. |
| `models` | Allowlist, compared case-insensitively. See [Model rules](#model-rules). |
| `rpm` | A token bucket of `rpm` per minute, with a burst of `rpm/2`. |
| `blocked` | `true` removes the peer from WireGuard. Its session dies at once and handshakes are refused. |

You can import an existing WireGuard client: put its public key in `public_key`, give it an `address`, and configure the client side by hand with the server's public key and `AllowedIPs = 10.77.0.1/32`.

## Roles

Built-in roles:

| Role | Allowed paths |
|---|---|
| `user` | `/`, `/api/version`, `/api/tags`, `/api/ps`, `/api/show`, `/api/chat`, `/api/generate`, `/api/embed`, `/api/embeddings`, `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/models`, `/v1/models/*` |
| `readonly` | `/`, `/api/version`, `/api/tags`, `/api/ps`, `/api/show`, `/v1/models`, `/v1/models/*` |
| `admin` | `*` |

Path patterns are exact matches (`/api/chat`), prefixes ending in `*` (`/v1/*`), or `*` for everything. A role in `roles:` with the same name as a built-in replaces it.

## Model rules

For a device with an allowlist, the proxy reads the whole request body, up to `max_body_mb`. It decodes the body with Go's `encoding/json`, which is what Ollama itself uses, so it sees the same model Ollama will load. That rules out tricks such as a nested `"model"` key, a duplicated key or a `MODEL` spelling. It falls back to the older `name` field for pull, delete and show. The buffered body is then sent upstream unchanged.

| Rule | Matches |
|---|---|
| `llama3.2` | `llama3.2` and `llama3.2:latest` |
| `llama3.2:1b` | only that tag |
| `qwen3:*` | every tag of `qwen3` |
| `*` | everything (same as an empty list) |

Requests without a body still work for allowlisted devices, as long as their role allows the path: listing models (`GET /api/tags`), running models (`GET /api/ps`) and the version. A request *with* a body must name an allowed model, or it gets `403`.

Devices without an allowlist are not buffered. The proxy peeks at the first 64 KB only to record the model in the access log, and large bodies such as images keep streaming.

## Path rules

Paths are matched before anything is forwarded. Requests with non-canonical paths, such as `/v1/../api/pull`, `//`, or percent-encoded segments, are refused with `400`, so they can't slip past a prefix rule.

## Client config (`<device>.yaml`)

```yaml
client:
  name: laptop
  private_key: aB3...=
  address: 10.77.0.2                  # this device's tunnel IP
  server_public_key: Wp8...=
  preshared_key: Z1x...=
  endpoint: vpn.example.com:51820     # DNS names are re-resolved every 5 minutes
  server_address: 10.77.0.1
  server_port: 11434
  listen: 127.0.0.1:11434             # where `connect` exposes Ollama locally
  keepalive: 25                       # seconds; keeps NAT mappings open
  mtu: 1420
```

`connect --listen` overrides `listen` for one run. Binding to `0.0.0.0` would share the tunnel with the whole LAN. Do that only on purpose, because everyone on that LAN then acts as this device.

## Hot reload

The server watches `server.yaml` and reapplies these within 2 seconds of any change:

- peers
- roles
- blocks
- firewall rules

Live sessions stay up. `SIGHUP` forces a reload. Changes to the `server` section (key, port, address, upstream) and to `admin.listen` need a restart. The server logs a warning when it sees one.

The dashboard writes its changes to the same file, so CLI edits, hand edits and dashboard edits all end up in one place.
